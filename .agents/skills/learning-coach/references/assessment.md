# 出题标准与公平反馈

## 先确定测什么

所有要用于评分或升级状态的题，都先固定题意和关键标准，再展示题目。先检查必要条件和资料是否充分。纯引导追问可以轻量进行，但没有预定标准的回答不能事后包装成正式通过测验。

题型必须明确：

- 源码行为：以指定版本的实际执行为准，先读代码；区别当前实现与建议改法。
- 生产设计：声明目标和约束，按正确性、失败处理、可验证性与权衡评价；允许多个合理方案。
- 概念/协议：基于适用范围与来源判定，区分项目约定与通用规则。

用户近期偏好生产原则和专业表达，复习默认按此出题；若要考源码，应在题干明确。不得把“Demo 直接 return”作为“生产系统必须无条件结束”的唯一答案。

## 保存紧凑评分记录

阶段验收、明确要求评分的测验共用 learning/assessments/<date>-<topic>-<task-key>.md；task-key 使用当前任务 ID 的可辨识片段，未知时使用不冲突的短标识。只在真的出题时创建文件，未来题不提前生成。

普通辅导与日常复习用轻量路径：出题前在当前上下文确定目标、假设与必要判据，不必工具写盘；答后按原判据反馈。学习块结束需要更新掌握/排期时，合并记录目标、关键判据、首答证据、提示程度与质量。上下文丢失且无法确认原判据时，不补造通过标准，另设新题验证。此路径与正式测验共用公平标准，不另建评分体系。

正式测验每题一个稳定 ID，出题前保存：

- 目标与场景；题干及关键假设。
- 依据：已读的代码符号/版本或资料链接。
- 判据：2–4 个必要点、可接受替代方案、不能违背的边界；事实题另记简短参考答案。
- 版本与状态：v1 / pending；结果留空。

这只是可审计答案标准，不记录隐藏推理。默认不向未作答用户展示答案文件或其内容；它是普通项目文件，并非保密或访问控制机制，用户要求查看时照常提供并把该题标为已暴露答案。

作答后重读标准，再追加：用户回答的简短忠实摘要、提示等级、正确/部分正确/错误/无法判分、满足与未满足点、0–5 质量分（仅可判分时）、与概念/错题的关联。评分映射沿用 review-system，不新建竞争分制。

## 标准错误与争议

不能因为用户自信或与教练预想不同而改标准。如果条件缺失、合理多解、引用错误或新证据推翻标准：说明题目问题，标为无法判分，保留原版本及撤销原因，新题/新标准升版本。不要把教练出错记进用户错题本。

若错误评分已写入 concepts/mistakes/queue，撤销该证据并仅据其余有效记录重新判断；保留修改说明，不盲目重置整个概念或删除其他历史证据。资料不足时状态待验证，而不是强判用户错误。

## 反馈与表达训练

先给内容判定与一条依据，再指出最关键缺口。按 profile，在作答后给一个短表达框架或改写示例，明确这是教练示范。因果正确但措辞口语化不能算概念错误；内容理解与表达改善分开反馈。

未独立完成就给下一档帮助；完成后用不同条件检验。输出保持自然简短，不逐项朗读内部评分表。计数、提示后成功与跨日规则继续沿用现有学习状态模型。
