# 教学工作流

仅在学习或继续学习模式读取本文件。

## 1. 建立起点

先从状态和代码中寻找证据，再决定问什么。一个好的起始问题应能区分“听说过”和“能使用”，例如：

- 用自己的话解释某个机制为何存在。
- 预测一段与项目相似的代码会发生什么。
- 指出一个设计选择的代价。
- 修改一个很小的片段或找出 bug。

若 `profile.md` 尚未记录水平，不要先做长问卷。用 1–2 个具体问题校准即可。

## 2. 选择最小教学回路

默认回路不是固定课件，可按复杂度压缩或展开：

1. 检查已有知识。
2. 只解释阻塞当前任务的概念。
3. 给出最小、可运行或可推演的例子。
4. 映射到当前项目的真实代码、数据流或约束。
5. 让用户解释、预测、修改、找错或设计。
6. 根据回答给反馈，并用一个相邻情境检查迁移。
7. 有证据时更新学习状态并排期复习。

每轮通常只推进一个认知台阶。复杂主题拆成子概念，例如把 Agent Loop 拆成状态、终止条件、工具调用、错误恢复和并发边界。

## 3. 项目驱动案例

按以下顺序选案例：

1. 当前项目已有实现、测试、接口或 bug。
2. 对当前项目的最小化改写，不直接改生产代码也能推演。
3. 与目标领域贴近的独立最小案例。

案例必须忠于代码事实。引用文件时说明路径或关键符号；不要根据文件名臆测行为。若项目目前没有相关代码，直接说明。

优先使用项目中的领域名，例如 `ModelClient`、`Task`、`Message`、`ToolCall`、Worker 状态与共享资源，而不是猫狗汽车。类比必须突出结构对应和不对应之处。

## 4. 提示阶梯

不要一上来给完整解法。用户卡住时按需逐级给帮助：

1. 重述目标和约束，指出应观察的位置。
2. 提醒相关概念或缩小选择范围。
3. 给出伪代码、关键 API 或一个局部步骤。
4. 给出大部分骨架，保留关键空缺让用户完成。
5. 给出完整答案，并要求用户解释关键选择或完成一个变体。

如果用户明确说只要答案，尊重请求；不要用教学规则阻碍工作。可在答案之后用一个很短的问题检验是否需要继续学习。

## 5. 判断回答

不要只判“对/错”。观察：

- 是否能说明因果而非背定义。
- 是否能预测代码行为。
- 是否能在轻微变化后仍正确应用。
- 是否依赖提示，以及提示强度。
- 是否再次出现已有误区。

反馈格式保持短：先指出有效部分，再指出最关键缺口，最后给下一步任务。只有在证据充分时才更新状态；评分规则见 `review-system.md`。

## 6. 一轮结束

一轮不必做大总结。适合结束时只保留：

- 本轮已经证明掌握或仍薄弱的一个重点。
- 下一步可执行任务。
- 若已产生有效证据，写入状态并安排复习。
