# s01 阶段面试：任务完成判据

## Q1 v1 · completed

- **目标与场景**：生产设计；模型给出最终回复、没有工具调用，但多步骤任务的 Todo 仍有 pending。判断任务是否结束及谁负责校验。题目不要求复述当前 Demo 的直接 return 行为。
- **关键假设**：Todo 为模型维护的计划状态，可能不准确；任务涉及可观察的工具副作用；系统必须避免无限自动续跑。
- **题干**：给出一套完成判断和失败处理方案，说明采用哪些证据、在哪一层校验、校验不通过后如何处理。
- **依据**：`AgentHarness/agent_loop.py` 的无 `tool_calls` 分支与 Stop hook；`learning/progress.md` 已记录的上一轮待答问题。生产设计可超出现有实现。
- **必要判据**：①不能仅以模型最终文本或 Todo 自报状态作为完成证据；②说出与目标匹配的外部可观察验收方式；③明确校验的职责/时机；④校验失败有有界续跑、报错或交还用户的出口。
- **可接受方案**：独立 verifier、Stop hook 中校验或上层 orchestrator 校验均可，只要职责清楚且不会让工具调用协议悬空；可按任务类型使用测试、文件/数据状态或人工确认。
- **边界**：不得把尚有 pending 无条件等同失败，也不得无限续跑；若证据不可获得，应说明不确定性及交接。
- **首答摘要**：用户主张在 agent loop 的 Stop 边界设置 handler；若曾创建 Todo，则触发模型校对并更新 Todo 状态。
- **首答判定**：部分正确，质量 2/5，未给提示。满足校验时机和一种职责放置方式；尚未给出独立于模型/Todo 的完成证据，也未说明校验失败的有界出口。后续追问另记，不回写首答分数。
- **当前追问目标**：检验 Todo 与模型复核都可能报告完成时，如何依据可观察结果判断是否结束。

## Q2.1 v1 · completed after hint

- **目标与场景**：协议/生产设计；同一 assistant 响应声明 `write_file`（ID `a`）和未知工具 `deploy`（ID `b`）。`write_file` 成功，`deploy` 没有 handler。
- **题干**：说明结果消息的数量、关联 ID、追加时机，以及为何不能在 `deploy` 处直接抛异常终止。
- **依据**：`AgentHarness/agent_loop.py` 中 `tool_calls` 遍历、handler 查询与 `messages.extend(results)`；OpenAI Chat Completions 的工具结果需要关联原始调用 ID。
- **必要判据**：①为 `a` 与 `b` 各追加一条结果，`b` 为可读失败结果；②两条结果分别带原始 ID，不能只保留成功调用；③完成当前批次后再请求模型；④说明异常中断会留下未闭合批次，或提出同等的协议/恢复理由。
- **可接受方案**：失败结果可由通用 unknown-handler 分支或工具执行包装器产生；结果可按调用顺序追加。允许对模型下一步是否续跑采用不同产品策略，但须保留用户交接出口。
- **首答摘要**：用户指出 ID 必须闭环以保证消息协议完整；对未知 `deploy` 返回如 `deploy not find` 的标准化提示，并认为 `a`、`b` 都应闭环。
- **首答判定**：部分正确，质量 3/5，未给提示。满足调用 ID 成对与未知工具失败结果两个要点；尚未明确 `a` 的成功结果、整批追加后才请求模型，以及直接抛异常为何造成协议中断。
- **修正尝试摘要**：用户再次说明整批应闭环，并给 `b` 插入未知工具结果；把后果表述为 LLM 认为工具未调用。
- **当前反馈**：仍遗漏 `a` 的成功结果和批次追加时机；已给出一档提示：未闭环首先违反 API 消息协议，而非模型主观误以为未调用。
- **修正后回答摘要**：明确 `a`、`b` 都要有对应工具结果，未匹配会使下一次 API 请求的消息序列不合法；整批追加后模型可改用其他工具。
- **最终判定**：纠正后正确，质量 3/5，得到一档提示。已覆盖全部必要点；`a` 的结果内容仍可更具体地说为写入成功及输出/摘要。因在提示后完成，不作为独立掌握升级证据。

## Q3 v1 · revision requested

- **目标与场景**：协议与权限边界迁移。assistant 同批声明 `write_file`（ID `a`）与 `deploy`（ID `b`）；PreToolUse 拒绝 `write_file`，`deploy` 仍无 handler。
- **题干**：循环应如何处理两条调用？说明 handler 是否执行、两条结果如何关联、何时进入下一轮。
- **依据**：`AgentHarness/agent_loop.py` 的 `trigger_hooks("PreToolUse", ...)`、`blocked` 分支、未知 handler 回退和 `messages.extend(results)`。
- **必要判据**：①被拒绝的 `a` 不执行 handler，但追加带 ID `a` 的拒绝结果；②`b` 追加带 ID `b` 的未知工具失败结果；③两条调用均有结果后才进入下一轮；④权限拒绝和未知 handler 分别属于执行前治理、分发失败，不能混为一类。
- **首答摘要**：用户认为工具通常顺序执行，`write_file` 失败后 `deploy` 也会装填失败状态，以保证消息协议完整。
- **首答判定**：部分正确，质量 2/5，未给提示。识别到两条调用都要有结果并可顺序处理；混淆了失败原因，尚未说明被拒绝的 `a` 不执行 handler，以及 `b` 是因为没有 handler 才独立失败。
- **当前提示**：每个 tool result 应描述其自身调用的真实结果，不能把前一个调用的拒绝传播为后一个调用的失败原因。
- **修正后回答摘要**：用户指出 `b` 的真实失败原因不是权限拒绝，并追问若 `b` 实际存在，是否会正常执行。
- **最终判定**：纠正后核心因果正确，质量 3/5，得到一档提示。已识别每个调用独立归因；关于批内调用依赖是有效的设计追问，已直接说明，不作为原题缺失。
