Agentic RAG：用证据缺口驱动有界决策

先理解原理，再沿同一个例子看演示、读代码、运行和做变式。

从“查一次”到“下一步查什么”

问题：“张老师指导过哪些参加项目X的学生？”首次检索只知道张老师的学生名单，缺少项目成员。固定单次RAG可能直接列出所有学生，或说不知道。Agentic RAG把检索作为工具，允许控制器根据当前证据选择下一步：查询项目成员、交叉验证名单、再生成结果。关键变化是信息缺口参与控制流，而不是仅仅加一层for循环。

Agentic与GraphRAG描述两个不同维度：前者关注谁决定下一步，后者关注知识如何组织和检索。Agent可调用向量、SQL、图查询；图检索也能放在固定流程里。它们可以组合，不能理解为单一升级阶梯。普通RAG的生成模型也有推理能力，“Naive RAG没有推理”是把检索管道与模型能力混为一谈。

控制器最少要知道什么

状态可以包含原始问题、约束、已确认事实、证据列表、尚缺字段、历史检索指纹、迭代次数、剩余token/时间预算和当前阶段。原问题不能被改写覆盖，否则系统会逐轮漂移。证据对象带source_id、适用条件和可信度，而不是不断拼字符串。历史指纹用于识别同一查询与同一结果的无进展循环。

候选动作包括直接回答、检索某源、改写query、拆分子问题、澄清、拒答和转人工。动作选择可由规则、分类器或LLM提出，执行层仍要做权限、参数和预算校验。控制器不能绕过底层授权；所有分支共享同一租户和数据访问边界。

相关、充分、支持是三次不同检查

检索评估先问文档与问题是否相关；覆盖检查问所需字段/子问题是否已满足；生成后支持检查问每个结论是否被证据支撑。检索到一篇有关老师的文章不等于掌握其全部学生，更不等于知道项目成员。资料充分也不保证生成不漏条件，必须分层验证。

已解例：状态needs={学生名单,项目成员}。第一次检索得到学生A、B，needs剩项目成员；第二次查到项目成员B、C，交集为B。此时才能生成“B”，同时引用两份名单。如果只有不完整项目报道，答案应是“已查证B参与；现有材料不足以列全”，不能把未检索到A当作A未参与的证明。

WORKED EXAMPLE / 从刚才的原理到这份代码

根据缺失字段推进检索

正文的集合例子就是这份程序：张老师的学生是{A,B}，项目成员是{B,C}，答案应为交集{B}。为把机制看清楚，实验把两份资料放在sources字典里，取代真实检索工具；state保存已得到的facts、尝试次数attempts和检索轨迹trace。接下来逐步观察这三个状态字段怎样改变。

循环先处理students，再处理project。第4行在行动前查预算，第6行递增次数，第7行把本次结果写进facts。第一次完成后只有students，第二次完成后两个字段才齐全。第10行检查字段覆盖，第11行求交集，最后打印answer: B。你可以在每一步同时看上方状态快照和下方对应代码，不需要想象它们如何对应。

边界分支只改第4行的上限，从2改成1。于是第一份资料取得后，第二次循环会直接break，facts里没有project；同一第10行条件不成立，进入第15行打印insufficient evidence。这正是正文“达到上限不是完成”的具体例子。实验没有自主LLM规划器，所以它训练的是证据覆盖与有界循环，不是宣称复现了自主研究Agent。

对应刚才的讲解：相关、充分、支持是三次不同检查。本案例的运行范围：人工字典替代检索工具，子问题顺序固定；实验只观察状态、证据覆盖和次数上限。

先把代码与概念对上

代码用确定性需求清单替代LLM规划，展示相同核心契约：动作前检查预算、结果写入状态、充分性与成功分开判断。它不是完整自主规划器。

完整参考实现 · 带行号供演示对照
sources = {"students":{"A","B"}, "project":{"B","C"}}
state = {"facts":{}, "attempts":0, "trace":[]}
for need in ("students", "project"):
    if state["attempts"] >= 2:
        break
    state["attempts"] += 1
    state["facts"][need] = sources[need]
    state["trace"].append(need)
    print(f"step{state['attempts']}: retrieve {need}")
if {"students","project"} <= state["facts"].keys():
    answer = sorted(state["facts"]["students"] & state["facts"]["project"])
    print("answer:", ",".join(answer))
    assert answer == ["B"]
else:
    print("insufficient evidence")
assert state["attempts"] <= 2

运行后应看到

step1: retrieve students
step2: retrieve project
answer: B
在同一案例上改一个条件 1：project返回None，应该如何区别于空集合？

None表示无法获取，不能完成证据需求；空集合若源声明是完整成员列表则可支持无人参与。状态需要记录完整性与获取状态。

在同一案例上改一个条件 2：同一查询返回相同结果时怎样停止？

记录(query,source,result_version)或结果指纹；重复且needs没有缩小时触发no_progress，不再盲目检索。

如何保证循环有意义地停止

正常停止是证据充分并通过输出校验；异常停止包括无可用数据源、预算耗尽、重复无进展、工具故障或权限拒绝。次数上限只是护栏，达到上限不意味着答案自动可用。保留已确认事实、说明缺口并拒绝不支持部分。不同故障需要不同恢复：空结果可尝试查询改写；权限拒绝不应换路径越权；外部写工具超时要先查询结果，不能盲目重试。

不要把“自我反思”当可靠性证明。模型自评可能重复确认自己的错误，必要时用确定性字段检查、独立证据或人工复核。复杂策略是否值得，应比较固定流程基线的质量、平均轮数、p95延迟和每成功任务成本，而不是把更多工具调用当更聪明。

审查教材中的示意代码

原文LangGraph代码属于思路草图：retry_count没有递增，refined_query没有明确初始化和更新，datasource没有真正控制检索器；generate到check的边缺失，check节点函数返回字符串却被当作状态节点使用；幻觉检查提示也没有把原证据明确传入。有文档即生成的判据混淆相关与充分。这些都是阅读即可发现的契约缺口，不能直接把原文当可运行参考实现。

本课用纯Python状态循环演示缺口如何缩小，避免框架API掩盖控制流。后面选择框架时再把相同状态和转移映射到具体节点；没有必要为了学习Agentic RAG先安装整套服务。

01 · 一次检索为空，就不断改写到成功，有什么问题？

对应概念：如何保证循环有意义地停止

展开参考答案与评分要点

没有预算和无进展判据会无限循环；知识库根本没答案时改写无法创造证据。应限次数/时间、检测重复、评估可用数据源，最后说明缺口或澄清，而不是为了结束而编答案。

检查：需有异常终止语义。

02 · 为什么GraphRAG不一定是Agentic RAG？

对应概念：从“查一次”到“下一步查什么”

展开参考答案与评分要点

图是知识表示与检索方式，Agentic是运行时控制策略。固定接收问题→图查询→生成没有动态选择下一步；Agent也可动态选择图或SQL检索，两者可组合。

检查：用两个维度解释。

03 · 所有检索段落都相关，能否生成完整答案？

对应概念：相关、充分、支持是三次不同检查

展开参考答案与评分要点

相关不代表覆盖所有子问题、例外与时间条件。需先定义回答所需证据，检查覆盖和冲突；有缺口时继续查或限定答案范围。

检查：必须说明覆盖而非只增加数量。

04 · 达到3轮上限，但只找到学生名单，该输出什么？

对应概念：如何保证循环有意义地停止

展开参考答案与评分要点

说明已找到的名单及引用，明确缺少项目成员资料，无法可靠给出交集或完整结论。允许部分回答需产品策略；不能把名单全部当项目成员。

检查：不将预算停止当成功。

容易踩的坑

  • 有文档就生成
  • 用固定轮数证明自治
  • 把模型自评作为硬保证

这一课的验收

独立设计正常、缺证据、预算耗尽、无进展四条结束路径。
