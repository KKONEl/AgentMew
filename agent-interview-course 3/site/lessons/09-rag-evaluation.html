一条错误答案背后可能有五种故障

用户投诉报销答案错误。直接换大模型可能掩盖问题：解析时漏了表头、向量库仍保留旧版、召回漏掉例外、重排把例外排出预算、生成器读到但没遵循，都会造成相同外观。因此评测要存证据轨迹：查询、版本、过滤条件、召回列表、最终上下文、答案、引用与调用开销。日志脱敏并受访问控制，不能为调试泄露制度或用户信息。

把链路分为数据、检索、上下文和生成四层。数据层先抽查真实文字与表格；检索层检查标注证据是否进入候选；上下文层检查必要条件是否被截断；生成层检查每个结论是否被证据支持。这是归因顺序，不是说所有失败只有一个原因。

指标到底在测什么

Recall@K是前K中找到的相关文档数除以所有应找文档数；前提是相关集合标注足够完整。MRR关注首个相关结果的倒数排名，更适合找到一条就有用的任务。nDCG允许多级相关性，奖励高价值结果排前。文档级命中不等于答案证据覆盖；一份长文被命中但关键页没进上下文，仍无法回答。

生成侧区分正确性（与参考事实一致）、忠实性（结论有当前证据支持）、相关性/完整性（回答了用户需要的内容）。模型可能碰巧答对500但上下文只有400，正确性可能高而忠实性低；也可能忠实复述旧制度400，但对当前业务事实错误。引用存在不等于引用支持该结论，应逐结论核验引用。

已解例：指标不能互相代替

设相关证据为A和B，系统返回X、A、Y。Recall@3=1/2，首条相关排名2，该题RR=1/2（MRR是多题RR的均值）。如果A是一般标准、B是适用的例外，找到了A并不够。候选阶段A、B都在前50而最终上下文只有A，问题是重排/截断；候选中根本没有B，则先排查召回与索引。对关键字段可建立“金额、单位、生效日期、例外条件”覆盖检查，不必每项都由LLM裁判。

WORKED EXAMPLE / 从刚才的原理到这份代码

检索指标手算器

刚才的已解例固定相关证据为{A,B}，返回列表为[X,A,Y]。下面展开这份指标函数：前3条只有A相关，因此Recall@3是1/2；第一条相关结果在第2位，所以单题RR@3也是1/2。两项数字碰巧相同，但分母来源完全不同。

演示与代码都先计算这组结果，再计算[A,B,X]：A、B都被找到，Recall变成1；第一条就是相关结果，RR也变成1。你可以对照第3行集合交集和第4行第一次命中的枚举位置，理解“覆盖了多少证据”和“最早多久遇见证据”的区别。MRR是多题RR取平均，这里函数返回的是单题RR。

最后用程序已有的空相关集合断言解释边界：relevant=set()时，Recall分母为零，所以返回None，不能当作100%召回。这条分支是数学定义处理，并非系统坏了。看完演示就运行同一函数，再按下方变式把列表改为[A,X,Y]，亲自确认Recall保持0.5而RR升至1。这样正文、演示、代码和习题都围绕同一个集合与排名展开。

对应刚才的讲解：已解例：指标不能互相代替。本案例的运行范围：这里只计算检索指标；答案事实核验与上线评测是后续独立步骤。

完整参考实现 · 带行号供演示对照
def metrics(ranking, relevant, k):
    top = ranking[:k]
    recall = len(set(top) & relevant) / len(relevant) if relevant else None
    rr = next((1 / i for i, d in enumerate(top, 1) if d in relevant), 0)
    return recall, rr

recall, rr = metrics(["X","A","Y"], {"A","B"}, 3)
assert recall == 0.5 and rr == 0.5
print(f"Recall@3={recall:.2f}, RR@3={rr:.2f}")
r2, rr2 = metrics(["A","B","X"], {"A","B"}, 3)
print(f"Recall@3={r2:.2f}, RR@3={rr2:.2f}")
assert metrics(["X"], set(), 1)[0] is None

运行后应看到

Recall@3=0.50, RR@3=0.50
Recall@3=1.00, RR@3=1.00
在同一案例上改一个条件 1：返回列表重复A，为什么不能把它计成两个相关证据？

用集合交集去重；重复文档不增加覆盖，且浪费上下文预算。

在同一案例上改一个条件 2：多跳题必须A、B齐全，如何补充指标？

添加all-required-evidence指标，判断relevant是否是top的子集；按问题聚合与按文档聚合分开报告。

如何建一个有用的测试集

从真实业务分层采样：简单事实、精确编号、多跳、全局综述、无答案、版本冲突、权限拒绝、模糊指代与表格。为每题保存业务时间、用户角色、参考证据ID、允许答案与拒答条件。训练/调参集与保留测试集分开，避免反复对测试题调参。比较两方案应使用相同数据快照、生成预算和测量条件；小样本差一点未必稳定，应报告样本量及不确定性。

LLM-as-Judge可以辅助检查，但裁判有位置偏见、措辞偏好和自我偏好。交换答案顺序、使用盲评、抽取人工复核并保留分歧样本。严禁把模型自评“grounded”当绝对真值。业务验收还需p95延迟、每任务成本、拒答质量和安全隔离；不能只报告平均准确率。

更新与删除为什么属于正确性

文档更新要使原文、chunk、向量和引用版本一致。可先构建新索引版本，再原子切换活动版本；旧会话如引用旧版需清楚标记。删除要覆盖向量、原文缓存、答案缓存和派生摘要，且有明确失效时限。缓存键包含租户、权限版本、知识库版本与query必要条件；仅用问题字符串会串租户或返回旧答案。

从实验走向上线

先做离线门禁，再小流量灰度，观察质量、延迟和成本变化，并保留回滚版本。线上点击率不完全代表事实正确，用户没投诉也不等于没错。面试中“用了RAGAS所以评测完成”信息不足：需要说清数据集、指标定义、人工校准、错误分层和真实改进证据。下面的手算实验让你识别Recall与MRR的区别，不假装完成了大规模RAG评估。

01 · 忠实但错误可能发生吗？

对应概念：指标到底在测什么

展开参考答案与评分要点

可能。上下文是过期制度，模型忠实回答旧金额，对当前事件却错误。必须让数据版本和适用范围先正确；忠实性只看当前上下文的支持，不能替代事实正确性。

检查：给出旧版具体反例。

02 · 检索Recall提高了，答案正确率下降，合理吗？

对应概念：已解例：指标不能互相代替

展开参考答案与评分要点

合理。更多候选可能引入冲突或噪声，最终预算挤掉重要例外，也可能生成器处理长上下文变差。比较最终上下文覆盖、排序、冲突率和答案，不能只看候选Recall。

检查：解释中间传导机制。

03 · 知识库更新后，答案缓存怎样处理？

对应概念：更新与删除为什么属于正确性

展开参考答案与评分要点

缓存键纳入知识库版本和权限版本，或通过事件失效关联答案；切换新版本后不应继续命中旧版。需要明确一致性时限和删除传播，测试旧引用与摘要。

检查：覆盖派生数据而非只删向量。

04 · LLM裁判判grounded，可以直接发布吗？

对应概念：从实验走向上线

展开参考答案与评分要点

不应单独决定。用标注集和人工校准裁判，检查引用及关键字段，设置安全和业务门禁，再灰度。裁判也会误判，需记录失败样本和回滚路径。

检查：裁判是有误差的测量组件。

容易踩的坑

  • 把无答案题强行标相关文档
  • 把自动裁判当真值
  • 只刷新向量忽略缓存与摘要

这一课的验收

用一个错答沿数据→召回→上下文→生成逐层排查，并给出可观察证据。
