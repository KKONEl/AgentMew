先理解问题：模型不知道你的内部制度

用户问“上海出差每晚能报销多少”，通用模型见过大量文本，也不代表见过你公司的新制度。把问题交给模型直接回答，它可能生成一个合理但无依据的数字。RAG（Retrieval-Augmented Generation，检索增强生成）先找到外部证据，再让生成模型结合问题组织答案。核心价值是把可更新、可追溯的知识引入当前推理上下文。它不会因为接入向量库而自动保证正确。

把它想成开卷回答：检索器负责翻到相关页，生成器负责阅读并作答。翻到的是旧版或别家公司的制度，阅读再认真也可能答错；翻到正确页，生成器仍可能忽略例外。因此首先把链路拆清楚，才能定位错误。

离线链路：文档如何变成索引

  1. 解析：从 PDF、Markdown、网页中取出文字与表格。保留文档名、页码、标题、版本、生效时间、租户与权限。扫描 PDF 需要 OCR 或视觉解析；解析漏掉表头，后面模型无法恢复原来的含义。
  2. 切块：以段落或标题为边界，超过长度再切。块是检索单元，不一定等于生成时的展示单元。块过小会失去主语和条件，过大会稀释主题并占用上下文。
  3. Embedding：将块编码为向量。它是一种检索表示，不是压缩后可还原的原文，也不负责生成回答。同一向量空间中的查询和文档表示才可比较；有的模型要求不同的 query/document 前缀。
  4. 存储：保存向量、块原文、稳定 chunk_id 和出处。只有向量没有原文，就无法给生成器提供证据；只有文档名没有页码和版本，就难以审计引用。

在线链路：问题如何成为答案

问题先做必要的意图识别和过滤，再编码为查询向量；检索系统取回候选块，按需要融合关键词召回和重排，最后在预算内构建上下文。生成模型收到的输入应明确区分用户问题和不可信文档，并要求证据不足时说清缺口。引用由 chunk_id 映射到原文位置，不能让模型随意编造页码。

离线：文档 → 解析 → 切块＋元数据 → 编码 → 索引
在线：问题 → 编码/查找 → 候选证据 → 上下文 → 生成 → 引用校验

已解例：同一个数字为什么有三个条件

证据 A：“2025版：上海住宿上限400元/晚。”证据 B：“2026版，自10月1日生效：普通员工上海住宿上限500元/晚。”用户是普通员工，出差日期为2026年10月20日。系统必须先基于身份和日期选用 B，再回答500元，并引用 B。语义相似度高的 A 不能只因排名靠前就覆盖 B。用户没提供职级而不同职级标准不同，应追问或列明条件，不能静默猜测。

这里至少有四类判断：相关性（谈住宿吗）、适用性（这位用户和这个时间适用吗）、充分性（有金额和单位吗）、真实性/权威性（是否可信制度）。不要把它们压缩成一个“相似度大于0.8就对”。

docs = [
 {"id":"old", "tokens":{"上海","住宿","标准"}, "year":2025,"limit":400},
 {"id":"new", "tokens":{"上海","住宿","标准"}, "year":2026,"limit":500},
 {"id":"food", "tokens":{"上海","餐饮"}, "year":2026,"limit":100},
]
query = {"上海", "住宿", "标准"}
allowed = [d for d in docs if d["year"] == 2026]
ranked = sorted(allowed, key=lambda d: len(query & d["tokens"]), reverse=True)
evidence = ranked[0]
assert evidence["id"] == "new"
print(f"答案：{evidence['limit']}元/晚；引用：{evidence['id']}")

每条记录和用户上下文都包含role；检索前同时匹配role和生效时间，不能生成后再过滤。

在同一案例上改一个条件 2：用户查2025年的出差，应如何改变查询契约？

请求携带business_date，按有效期选历史版本；不能无条件year==2026。

RAG 与微调、长上下文的边界

微调主要改变参数中的行为与模式，不是频繁更新制度的默认方法；RAG更新外部索引即可，但仍要处理删除和权限传播。长上下文能放更多材料，但成本、延迟和内容选择依然存在。小文档直接放上下文可能更简单，无需为了使用RAG而引入数据库。精确订单金额更适合带授权的SQL/API查询，不能靠相似文本估计。

面试表达如何有因果

不要只说“先向量化再检索”。先讲业务为什么要外部知识，再区分离线索引与在线问答，接着讲出处和失败路径，最后说明如何评测。检索召回、上下文选择和答案忠实性分别观测，才能解释“答案错了究竟是哪一步”。下面实验用词项匹配替代真实Embedding，让你看清数据流；它不是生产向量检索的效果证明。

01 · 为什么不能把向量直接交给聊天模型当作原文？

对应概念：离线链路：文档如何变成索引

展开参考答案与评分要点

检索向量用于比较和排序，通常无法还原文本。要用向量命中的chunk_id取回原文与元数据，再将原文作为生成模型上下文。除非模型接口专门支持此表示，数字数组并不携带可读证据。

检查：必须区分检索表示、原文、生成输入。

02 · 最新制度排名第二，旧制度排名第一，应如何处理？

对应概念：已解例：同一个数字为什么有三个条件

展开参考答案与评分要点

按用户身份、查询时间和文档生效范围过滤或排序，并保留版本。最新版不一定适用于历史出差，必须区分提问时间和业务事件时间。冲突无法判定时展示冲突、追问或转人工。

检查：不能只答“选新文档”；需业务时间。

03 · 检索到了“优先协议酒店”，能回答住宿上限吗？

对应概念：在线链路：问题如何成为答案

展开参考答案与评分要点

不能。它相关但缺少金额、单位及适用条件。继续检索标准表或明确说明证据不足，不要将模型记忆里的数字补作制度。

检查：区分相关和充分。

04 · 20页稳定制度是否必须使用向量数据库？

对应概念：RAG 与微调、长上下文的边界

展开参考答案与评分要点

不必。可先比较全文上下文、关键词查找和轻量索引，在质量、成本、延迟与更新需求下选择。检索是解决证据选择问题的手段，不是架构必选组件。

检查：提出可比较的简单基线。

容易踩的坑

  • 丢掉引用页码和版本
  • 把关键词小实验误认为向量模型
