MCP：Host、Client、Server 与工具数据流

先理解原理，再沿同一个例子看演示、读代码、运行和做变式。

建议学习 75 分钟起 · 先修：03 · 原理 → 同例演示 → 同份代码 → 练习

  • 按组件职责解释 MCP 协议边界

① 原理讲解→② 同例演示→③ 同份代码→④ 变式练习

场景：同一个助手接入三个系统

一个企业助手要访问代码仓库、内部文档和工单系统。如果每个接入都自定义一套发现工具、描述参数、发送调用和解释结果的方式，接入方与应用之间会出现大量重复适配。MCP（Model Context Protocol，模型上下文协议）为应用与外部能力提供者建立统一交互约定。它解决的是能力接入与上下文交换的协议问题，并不替你决定任务如何规划，也不自动保证工具安全。

教材以稳定架构和数据流为主。MCP 仍会演进，具体请求元数据、发现机制、传输和能力声明应以项目锁定版本为准。编写时核验的官方 latest 指向 2026-07-28；早期资料常出现连接初始化、旧 HTTP+SSE 等表述，不能把这些旧实现细节背成所有版本永恒成立的定义。本课演示仅模拟协议形状，不是可上线的完整 MCP 实现。

三个角色各自负责什么

Host 是承载用户交互、模型集成和策略控制的应用，例如桌面助手或 IDE。Client 是 Host 中与特定 Server 交互的协议组件。Server 提供聚焦的外部能力，例如查询工单、读取受权文档。一个 Host 可以管理多个 Client；每个 Client 面向一个 Server，这是职责映射，不应被误讲成“所有版本都必须一直保留一条网络长连接”。

可以用餐厅作类比：Host 像决定顾客需求和服务规则的前台，Client 像负责与特定厨房对接的服务窗口，Server 像提供菜品的厨房。这个类比只帮助分工，权限和数据处理仍要落到代码。Server 不应默认获得用户完整聊天历史，Host 只传递本次工具操作必要的数据，也应控制不同 Server 之间的数据流。

工具发现与模型 schema 不是同一步

应用通过 MCP 发现 Server 暴露的工具，例如 tools/list 返回工具名、说明与 inputSchema。此时工具定义到达的是 Host 的协议层，还没有天然变成模型的可调用工具。Host 需要按当前任务、身份权限和预算选择子集，处理命名冲突，并转换成所用模型接口接受的工具描述格式。

假设文档 Server 和工单 Server 都暴露 search。模型只看见一个 search 会产生歧义。Host 可以为模型命名为 docs_search 和 tickets_search，并保存映射表。模型提出 tickets_search 时，Host 通过映射找到对应 Client，再发送该 Server 的 tools/call，参数中的真实工具名仍是 search。这个适配层同时连接两种契约：Server 的 MCP schema 与模型接口的工具 schema；二者可能相似，却不能未经检查就假定完全一致。

一次调用如何往返

以“查工单 T42 状态”为例。Host 获取当前用户的可信身份和可用能力，发现工单工具，向模型提供已筛选的描述。模型返回候选调用及调用标识。Host 校验参数与策略，Client 发起工具调用，Server 再次验证凭据与资源访问范围，返回结构化状态。Host 对结果限制体积并关联模型调用 ID，把观察送回模型，模型再生成用户可读结论。

这里至少有三种标识：模型工具调用 ID 用于把观察配回消息，JSON-RPC 请求 ID 用于协议请求响应关联，业务幂等键用于写操作跨重试去重。它们解决不同问题，不能因为都叫 id 就混成一个字段。只读查询不需要业务幂等键也应有请求关联和审计；创建工单则需要处理上一课讲的提交后超时未知状态。

完整参考实现 · 带行号供演示对照
class Server:
    def __init__(self, label):
        self.label = label
    def list_tools(self):
        return [{"name": "search", "inputSchema": {"type": "object"}}]
    def call(self, request):
        assert request["method"] == "tools/call"
        assert request["params"]["name"] == "search"
        query = request["params"]["arguments"]["query"]
        return {"jsonrpc": "2.0", "id": request["id"],
                "result": {"text": self.label + ":" + query}}

servers = {"docs": Server("document"), "tickets": Server("ticket")}
routes = {}
for namespace, server in servers.items():
    for tool in server.list_tools():
        routes[namespace + "_" + tool["name"]] = (server, tool["name"])
model_call = {"id": "model-8", "name": "tickets_search", "arguments": {"query": "T42"}}
server, real_name = routes[model_call["name"]]
request = {"jsonrpc": "2.0", "id": 19, "method": "tools/call",
           "params": {"name": real_name, "arguments": model_call["arguments"]}}
response = server.call(request)
assert response["id"] == request["id"]
observation = {"tool_call_id": model_call["id"], "text": response["result"]["text"]}
assert observation["text"] == "ticket:T42"
print("available:", ",".join(sorted(routes)))
print("observation:", observation["tool_call_id"], observation["text"])

运行后应看到

available: docs_search,tickets_search
observation: model-8 ticket:T42

在同一案例上改一个条件 2：怎样拒绝模型请求未暴露的 admin_delete？

在索引 routes 前检查 name in routes，缺失时返回 unknown_or_forbidden_tool，不能动态执行同名 Python 函数。

Server 有哪些能力，边界又在哪里

Tools 表示可执行操作；Resources 表示可读取的上下文资源；Prompts 表示可复用提示模板。它们的具体呈现方式由 Host 设计，不能假定“提供了资源，模型就自动读完”。Host 仍需决定什么时候读、读多少、如何标注来源，以及哪些内容可以进入当前上下文。Server 返回一段“忽略之前规则”的文字，只能当作外部数据，不能提升为系统授权。

工具元数据中的只读性、破坏性等描述可以辅助界面与策略，但不能替代后端权限。即使 Server 说自己只读，Host 仍要按实际能力配置策略；Server 也不能只因请求来自 Host 就跳过资源归属检查。对于远程接入还需要明确认证、凭据作用域、传输保护与审计。协议统一的是消息契约，不会替业务承担全部风险。

如何避免版本型面试陷阱

不要把 MCP 简化成“JSON 包一层 HTTP”。JSON-RPC 是消息约定，传输是承载消息的方式，工具发现和权限是应用与服务协作的语义。也不要把某一时期的初始化握手、SSE 长连接或 SDK 写法当作协议的全部。回答时先明确“我项目锁定的是哪个版本”，再说明架构不变的职责与该版本的具体交互。跨版本迁移需要检查能力声明、元数据、错误和结果类型，并做兼容性测试。

面试可以这样表述：“MCP 帮助 Host 通过 Client 接入 Server 的能力。发现结果先到 Host，再经权限筛选和模型 schema 适配；模型提议调用后，Host 校验并路由，Server 做最终资源授权，结果按调用标识返回模型。协议不替代计划器、业务幂等和安全边界。”版本细节参见 官方架构 与 官方工具说明。本课其余场景和实验是教练补充，原文主题不能替代规范。

01 · tools/list 返回以后，为什么模型可能还看不到工具？

对应概念：工具发现与模型 schema 不是同一步

展开参考答案与评分要点

发现结果首先由 Host 收到；Host 还需按权限、任务、预算选取工具，转换成模型接口支持的 schema 后加入请求。没有暴露给本次模型调用的工具，不会因 Server 已安装就自动可用。

检查：分开协议发现与模型请求装配。

02 · 两个 Server 都有 search，如何避免错路由？

对应概念：工具发现与模型 schema 不是同一步

展开参考答案与评分要点

Host 为模型建立有命名空间的外部名，如 docs_search 和 tickets_search，并维护外部名到 Client 与 Server 内工具名的映射。执行时先查映射而非按字符串猜测，结果也保留来源。

检查：包括命名、映射、结果来源。

03 · MCP 是否意味着 Server 能看到完整聊天记录？

对应概念：三个角色各自负责什么

展开参考答案与评分要点

不意味着。Host 应只发送操作必要参数和受控上下文，控制跨 Server 信息交换。Server 不能因为提供工具就默认获得完整对话或其他 Server 的数据。

检查：说明最小必要数据与 Host 隔离职责。

04 · 如何回答“MCP 只支持 HTTP+SSE”这个说法？

对应概念：如何避免版本型面试陷阱

展开参考答案与评分要点

先说明该表述把特定版本或传输方案泛化了。MCP 的角色与消息语义和具体传输应分开，检查项目锁定规范和 SDK 支持的传输；不要用旧资料推断当前全部实现。

检查：辨析版本与协议层，不需要背未经核验的传输清单。

容易踩的坑

  • 认为接入 MCP 自动完成模型工具注册
  • 把协议 ID、模型调用 ID 和业务幂等键混用
  • 把旧版传输和初始化行为当作全部版本的固定事实

这一课的验收

能手绘发现与调用两条链，并解释 Host 的 schema 适配、名称映射、权限筛选和结果关联职责。
