不先追热点，先说清失败在哪里

用户只有几个口语词，相关文档却用专业术语，属于表示差距；需要跨章节综合，属于层级覆盖；答案在图片表格，属于解析和模态问题。HyDE、RAPTOR和多模态检索分别提供不同方向，不是把名字全部堆进同一管道效果就最好。每增加一步都要说明输入、输出、误差和成本。

HyDE：假想文档是检索探针

HyDE先针对query生成一份假想文档，再对它编码，借助文档式语义表达去检索真实资料。关键是检索仍落在真实语料，假想内容不能作为回答依据。假想文档可能错误、偏题，关键词和领域设定也可能误导检索，效果必须与直接query embedding比较。HyDE论文

已解例：用户问“数据库写完却通知丢了”，假想描述可能扩展为“transactional outbox，数据库事务和消息投递一致性”。这些术语有助召回，但如果假想文档编造“该框架默认启用outbox”，最终回答必须丢弃这项断言，只根据真实资料确认。工程上可保留原query一路，融合扩展召回，并记录哪一路贡献了正确证据。

RAPTOR：把长文本组织成多层摘要

RAPTOR将文本块进行语义聚类并递归摘要，形成不同粒度的检索单元。叶子保留细节，上层提供跨块概括，能帮助需要综合的问题。它的层级来自文本语义聚类，与GraphRAG基于实体关系及社区组织不同。论文采用的具体聚类细节不能简单背成“必定K-Means”；教学图只是机制简化。RAPTOR论文

摘要是一种有损表示。把三条互相冲突的结论压成一句“总体支持”会抹去争议；应保留父子来源，必要时沿摘要回到叶子证据。检索高层节点只说明主题可能有关，不保证每个精确数字都在上层。上下层同时进上下文时要去重，防止同一事实重复占预算。

WORKED EXAMPLE / 从刚才的原理到这份代码

从摘要回到叶子证据

本课前面列了HyDE、RAPTOR和多模态三条不同改进路线。为了不把它们混成一个程序，这里只对RAPTOR式“多层节点与原文回溯”做一个最小机制实验：人工给定三个叶子a、b、c，以及两个父主题“检索质量”和“工具治理”。a的原文是检索延迟高，b是检索召回不足，c是工具需要权限。它们就是紧接着代码里的leaves与parents，不是另一套假想文档案例。

用户的查询只含“检索”。第4行在父主题名上匹配，命中“检索质量”；第5行沿parents把它展开成叶子ID[a,b]。第8行再用这些ID回leaves取出真正文字。这样能清楚区分两个动作：高层主题帮你缩小范围，叶子保留具体证据。最后的断言检查回溯结果确为a、b。

边界分支故意跳过“父主题→叶子ID”映射，直接把“检索质量”拿去leaves查。程序会在第8行KeyError，因为父节点标题不是叶子键。这正对应正文要求保留父子来源关系，不能只检索到一个高层概括就假设已拿到原始细节。看完这个例子后再比较HyDE的检索探针和多模态页面路线；它们的原理有讲解，但这份小程序没有实现那些模型。

对应刚才的讲解：RAPTOR：把长文本组织成多层摘要。本案例的运行范围：层级已人工给定，程序只验证父主题到叶子的回溯，不执行真实聚类或摘要生成。

完整参考实现 · 带行号供演示对照
leaves = {"a":"检索延迟高", "b":"检索召回不足", "c":"工具需要权限"}
parents = {"检索质量": ["a","b"], "工具治理":["c"]}
query = "检索"
hits = [p for p in parents if query in p]
ids = [child for p in hits for child in parents[p]]
print("summary:", ",".join(hits))
for child in ids:
    print(child, leaves[child])
assert ids == ["a","b"]

运行后应看到

summary: 检索质量
a 检索延迟高
b 检索召回不足
在同一案例上改一个条件 1：高层摘要写“检索完全正常”而叶子写有问题，哪个优先核验？

回原文核验并标记派生摘要错误，重建受影响父节点；摘要不是超越原始证据的真值。

在同一案例上改一个条件 2：一个叶子被多个摘要引用如何避免重复？

用稳定leaf_id去重并合并来源路径，不能只按摘要文本计数。

多模态文档：先保护结构

财务PDF里的表格，列标题可能写“元/人/天”，如果只提取出100、200、300，数字失去意义。方案可以是结构化解析表格并保留标题、用视觉模型理解页面、或用文档图像检索模型索引页面。图像向量和文本向量并非天然可比较，必须确认模型是否定义共同表示以及所支持的检索形式。

表格适合精确聚合时，解析到结构化表再用SQL/代码计算，通常比让模型从文本估算更可靠。页面图像保留布局，但仍有分辨率、密集表格、图例理解和OCR错误问题；结果应关联页码与区域坐标，引用可定位到真正证据。多模态模型能看图片，不代表它的视觉注意与坐标引用一定准确。

数据库与Embedding怎么选

不按所谓“最大支持多少亿”背表。先写硬约束：数据量和向量维度、更新删除频率、租户过滤、混合检索、p95延迟、可用性、已有运维体系和预算。Embedding在目标语言、精确实体和长文本上的业务Recall比通用榜单名次更直接；更换模型通常需重建文档向量，不能把旧空间与新query混用。索引库与完整数据库也有持久化、过滤、复制和备份方面的差异。

一个可执行的实验顺序

先建立解析正确的简单检索基线和分层测试集，再只增加一个变量：若短问句召回差，尝试改写/HyDE；若跨段综合差，比较层级摘要；若证据在图表，先修解析或视觉路径。记录增益在哪个子集、开销增加多少、是否引入安全与版本风险。最后再组合真正互补的改进。

本实验用手工层级和关键词展示摘要命中如何回溯叶子，不进行真实聚类、Embedding或LLM摘要。你应能解释每一层的角色，再把玩具机制换成真实组件；不能把它的输出当作论文效果复现。

01 · HyDE编造了事实，为什么仍可能有检索价值？

对应概念：HyDE：假想文档是检索探针

展开参考答案与评分要点

它作为表示扩展可能包含有用术语，帮助命中真实文档；最终证据来自真实语料。不能保证编造不会误导，需与原query对照并验证实际收益，不能把假想文档作为引用。

检查：明确检索探针与事实来源。

02 · RAPTOR和GraphRAG相同点与差别？

对应概念：RAPTOR：把长文本组织成多层摘要

展开参考答案与评分要点

都可用层级摘要支持跨局部的理解；RAPTOR围绕文本语义聚类递归摘要，GraphRAG的具体方法常围绕实体关系图和社区。构建依据、适合任务和误差来源不同。

检查：不能只答树和图外形不同。

03 · 更换Embedding但不重算旧文档向量可以吗？

对应概念：数据库与Embedding怎么选

展开参考答案与评分要点

通常不可。新旧向量空间即使维度相同也不保证可比较。需重建索引、版本化切换并对照评估；特殊对齐方案也要验证，不能默认兼容。

检查：相同维度不代表相同空间。

04 · 表格里的数字都提取到了，解析就合格了吗？

对应概念：多模态文档：先保护结构

展开参考答案与评分要点

未必。需要单位、行列标题、合并单元格、脚注与页码。数字与条件关联丢失会产生错误金额，抽样对照原页并测试精确查询。

检查：说明结构与语义关联。

容易踩的坑

  • 假定任意图像文本向量可比较
  • 用过时选型表直接下决定
