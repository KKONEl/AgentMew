为什么一个检索器解决不了所有查询

“ERR_CONN_431是什么”需要精确错误码；“系统老是连不上”需要理解口语意图。词项检索擅长前者，稠密向量往往更能处理后者，实际强弱要在业务集验证。混合检索不是把两个分数直接相加：BM25分数与余弦相似度的量纲、分布不同，未经标定就平均，权重没有清晰含义。

BM25可理解为经过词频饱和与文档长度归一化的加权匹配：出现稀有词更有信息，重复100次不会比10次强10倍，长文不能只因词多占优。向量检索比较训练得到的语义表示，但罕见实体、否定条件、时间和精确数值未必可靠。先标注真实失败样本，再决定是否增加一条召回路径。

先切对，再谈模型升级

Markdown可按标题形成章节，再对过长部分按段落切分并保留标题路径。PDF要保留页码、表格表头与行列关系。子块负责精确命中，父块负责补上下文，这叫父子索引。检索命中“500元”却不知道是哪类人员，说明块边界破坏了条件；整份手册成为一块则容易让相似度偏向泛主题。

Overlap帮助边界处信息覆盖，但会制造重复块、增加存储和占用上下文，不能无上限增加。测试集应包含跨边界句、表格、长标题、例外条款与重复内容。只有比较检索Recall、最终答案质量和成本，才能说一个chunk方案更好，而不是背固定512或1024。

候选召回与最终重排是两件事

召回阶段追求在可接受开销内把证据纳入候选集。ANN（近似最近邻）牺牲部分精确性换速度；索引参数影响延迟与召回。Reranker通常联合阅读query与document，输出相关性排序，计算较贵，适合处理较小候选池。证据从未进入候选集，重排没有办法凭空找回来。

一个常见流程是：权限与版本过滤 → 两路各召回若干 → 按chunk_id去重 → RRF融合 → rerank → 按预算选上下文。数量只是调参起点，不是标准答案。去重时不要只按标题，同名制度不同版本可能不同；也不能在生成后才做ACL过滤，因为不该暴露的内容已经进入模型。

已解例：手算 RRF

Reciprocal Rank Fusion使用排名而不是原始分数：每一路给文档贡献1/(c+rank)。假设c=60，A在关键词第1、向量第3，B在关键词第2、向量第1。A=1/61+1/63≈0.032266，B=1/62+1/61≈0.032522，B融合更高。文档缺席某路时该路贡献0。c越大，不同靠前排名之间的差距越小，稳定跨路出现更有价值。

RRF不是相关性证明；两路都把一条过期制度排高，它仍然过期。候选融合与业务约束是不同层。用标注集比较Recall@K、nDCG、答案指标和p95延迟，记录每路独有召回，才能解释新增复杂度的价值。

WORKED EXAMPLE / 从刚才的原理到这份代码

手算与验证 RRF

正文刚手算了A与B的RRF分数，现在就用完全相同的A、B、C与两份排名运行程序。这个实验只研究排名融合：两条已得到的排名怎样合成一条？第一路是[A,B,C]，第二路是[B,C,A]，常数c=60。

rrf先创建空分数表，再按每一路排名累加1/(60+rank)。rank从1开始，因此第一名贡献1/61。第6行的dict.fromkeys先消除同一路重复ID；同一文档跨两路出现可以累加，同一路把自己重复列两遍却不能多拿一票。两路完成后，第8行按负分数升序，也就是实际分数降序排列；文档ID作为同分规则。

下面演示会把B=0.032522、A=0.032266、C=0.032002与最后打印结果接在一起。边界分支故意让第一路重复A，并去掉去重操作，观察A如何被刷到第一。这不是新的系统架构，而是检查RRF实现为什么需要一个具体的数据不变量。演示末步看到的三行结果，就是紧接着程序的预期输出。

完整参考实现 · 带行号供演示对照
from collections import defaultdict

def rrf(lists, c=60):
    scores = defaultdict(float)
    for ranking in lists:
        for rank, doc in enumerate(dict.fromkeys(ranking), 1):
            scores[doc] += 1 / (c + rank)
    return sorted(scores.items(), key=lambda x: (-x[1], x[0]))

result = rrf([["A","B","C"],["B","C","A"]])
assert result[0][0] == "B"
for doc, score in result:
    print(doc, f"{score:.6f}")

运行后应看到

B 0.032522
A 0.032266
C 0.032002
在同一案例上改一个条件 1：只在向量路出现的D，贡献如何计算？

另一条路不贡献，不是赋最后一名；D得到1/(c+rank)。

在同一案例上改一个条件 2：设计一个文档在两路第2，另一个只在一路第1的例子。

c=60时双第2为2/62≈0.032258，高于单第1的1/61≈0.016393，说明跨路支持的重要性。

Query改写与检索预算

用户说“那个额度呢”，需要先从会话恢复指代对象，再形成独立检索问题。改写不能篡改数字、否定、时间和用户限制。可保留原query与改写query双路检索，并记录版本和命中差异。HyDE是后面介绍的另一种表示扩展，不能把假想回答当证据。

Lost in the Middle指模型利用长上下文时可能对中间信息利用不佳，但不能据此认定所有模型永远只看两端。优先精简噪声、把关键证据按明确结构组织，再实测不同位置。没有上下文质量测试，单纯扩大窗口常常只增加成本。

01 · 为什么不能直接把BM25和余弦分数各乘0.5？

对应概念：为什么一个检索器解决不了所有查询

展开参考答案与评分要点

两路分值范围、分布和相关性含义不同，0.5并不等价同等贡献。可先用排名融合建立基线，或用标注数据校准分数、训练融合器，并验证目标分布。

检查：解释量纲和可评测替代。

02 · 召回Recall@50低，换reranker能解决吗？

对应概念：候选召回与最终重排是两件事

展开参考答案与评分要点

不能解决候选缺失。先检查解析切块、查询表示、过滤、索引近似参数；reranker只能重排已有候选。如果候选证据齐全但Top5差，才优先排查重排与截断。

检查：明确阶段边界。

03 · chunk加大一倍有什么可能结果？

对应概念：先切对，再谈模型升级

展开参考答案与评分要点

条件更完整、跨段信息更连贯，但主题变混、向量表示稀释、上下文token增加。需在同数据与相同生成预算下对照评测，报告正确率和成本，不假定单向改善。

检查：同时说收益、代价与控制变量。

04 · RRF排第一的文档是否能直接回答？

对应概念：候选召回与最终重排是两件事

展开参考答案与评分要点

不保证。融合依据检索排名，仍需权限、生效范围、证据充分性与冲突处理。排名是选择候选的信号，不是真值。

检查：不把排序分数解释为事实概率。

容易踩的坑

  • 用阈值0.8跨模型解释正确率
  • 先召回后才隔离租户
  • 假定更大块或更多TopK必然更好

这一课的验收

给出一个召回失败和一个排序失败，分别设计最小验证。
