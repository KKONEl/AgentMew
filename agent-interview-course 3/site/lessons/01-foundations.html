从一个会说错话的客服开始

用户问：“订单 A17 昨天退款到账了吗？”模型可能写出非常自然的回复：“已到账，请查收。”句子顺畅只证明它符合语言规律，不证明它连接过支付系统。本课先建立一个后续所有 Agent 设计都依赖的边界：语言模型能够根据输入产生候选输出；订单状态、用户身份、支付是否完成，需要外部可验证的证据。教材中的场景和代码属于教练补充演示，原文中的面经整理是学习线索，不代表公司官方标准答案或全部经过独立核实的亲历记录。

模型到底在做什么

对常见自回归语言模型，可以把生成理解为：在已有序列条件下计算下一个 token 的概率分布，再选择一个 token，加入序列，重复直到停止。token 是模型分词器的离散单元，可能是一个词、词的一部分、标点或字节片段。中文一个字不总等于一个 token，英文一个单词也不总等于一个 token。因此字符数只能做粗估，生产预算需要使用对应模型的计量方式，并把消息包装和工具定义算进去。

模型参数是在训练中形成的统计结构；上下文是这一次推理可见的材料，两者不是同一个存储层。把“我的名字是小林”放进当前对话，可能让后面的回复使用这个名字，并不等于更新了模型权重。应用把历史保存在数据库，也不表示模型自动看得到：只有被选取并组装到本次输入的内容，才属于当前可见工作集。所谓“模型记住了”应进一步追问，是仍在上下文、检索命中了记忆，还是参数中的一般知识。

上下文窗口是容量约束，不是可靠性承诺

上下文窗口描述单次推理可处理序列的容量边界，实际输入和输出限制还取决于接口与模型。工程上先取得窗口和输出的真实约束，再给回答或工具参数预留空间，最后分配指令、任务状态、工具 schema、历史和证据的输入预算。假设教学系统总预算 100 单位，预留输出 20，固定指令 10，工具定义 15，那么剩下 55 才能装用户问题、历史和证据。直接塞满 100 再要求输出 20，没有留下生成空间。

输入能放进去，不代表每个位置的信息都会被同等可靠地利用。相似资料可能互相干扰，早期否定约束可能被后面的噪声淹没。因此优化目标是让关键证据被正确使用，而不是把窗口填满。遇到超长日志，先在工具侧过滤字段、聚合统计并保留原文引用；不能先把几十兆日志发给模型，再让它替你解决入口体积问题。

采样为何让同一个问题出现不同回答

假设三个候选 token 的原始概率为 0.6、0.3、0.1。贪心选择始终挑第一名；采样则按分布抽取，第二名和第三名仍有机会出现。temperature 常通过对 logits 缩放改变分布的尖锐程度：较低温度通常更集中，较高温度通常更分散。top-p 则保留累计概率达到阈值的候选集合，再在集合内采样。二者作用不同，而且供应商支持的参数和细节需要查接口说明。

低温适合需要稳定格式的任务，但不是事实校验器。如果概率最高的续写本身是错误退款状态，稳定选择它只会稳定地说错。即便使用确定性解码，部署、并行计算和后端变化也可能影响严格复现；不要向业务承诺“温度为零，任何条件下都逐字一致”。实验只演示选择策略，不能证明任何真实模型的准确率。

把一个错误回复拆成可验证链路

现在重新处理订单问题。第一步提取订单标识 A17，但不从模型文本接受用户身份。第二步由运行时认证身份，查询该身份可访问的订单。第三步取得支付服务返回的状态、查询时间和流水号。第四步仅根据这些字段回答：“截至本次查询，退款处理中。”如果工具超时，回复应指出暂时无法确认，并保留查询或重试入口，不能把缺少结果补成“已到账”。

这条链路同时区分事实正确性、依据忠实性和任务完成度。回答“处理中”可能恰好符合真实状态，但若模型没有查询也没有证据，它仍缺少可追溯依据。反过来，忠实复述一份过期状态也可能不满足用户对“现在”的要求。评测需要分别检查证据来源、时间范围、结论与证据是否一致，而不是只看语言是否礼貌。

WORKED EXAMPLE / 从刚才的原理到这份代码

用小概率表理解采样与预算

把订单 A17 的退款状态问题缩成下方同一张概率表：candidates 是 paid、pending、unknown，分别表示“已到账”“处理中”“未知”，weights 固定为 0.6、0.3、0.1。greedy 在第 6 行取最大权重，因此必为 paid；samples 用种子 7 抽样 100 次，counts 的键覆盖三个候选，演示相同分布可以产生不同选择。

window=100、reserved_output=20，以及 rules=10、tools=15、history=35、evidence=20，恰好满足 80 输入加 20 输出的预算。注意变量名 evidence 只是预算分类，并没有真正装入支付证据。最后 fact verified: False 是明确写出的边界提示，不是已经运行的事实核验器。

因此请先用演示追踪选择与预算，再回看正文认证、查询和证据核验链：那些是生产系统需要补齐的环节，代码目前没有实现。变式只把 history 从 35 改成 45，就会先在预算断言处停止，四行正常输出都不会出现。

对应刚才的讲解：把一个错误回复拆成可验证链路。本案例的运行范围：概率表用于观察采样与窗口预算，不查询真实订单，也不运行语言模型。

完整参考实现 · 带行号供演示对照
import random
from collections import Counter

candidates = ["paid", "pending", "unknown"]
weights = [0.6, 0.3, 0.1]
greedy = candidates[max(range(len(weights)), key=weights.__getitem__)]
rng = random.Random(7)
samples = rng.choices(candidates, weights=weights, k=100)
counts = Counter(samples)
assert greedy == "paid"
assert len(counts) == 3
window, reserved_output = 100, 20
parts = {"rules": 10, "tools": 15, "history": 35, "evidence": 20}
assert sum(parts.values()) + reserved_output == window
print("greedy:", greedy)
print("sampled categories:", ",".join(sorted(counts)))
print("input budget:", window - reserved_output)
print("fact verified:", False)

运行后应看到

greedy: paid
sampled categories: paid,pending,unknown
input budget: 80
fact verified: False
在同一案例上改一个条件 1：把历史改为 45，会触发哪条断言？怎样在不删证据的条件下恢复？

总量变为 110，预算断言失败。将历史压缩回 35，或按新配置减少其他可省内容 10；不能凭空扩大窗口。

在同一案例上改一个条件 2：增加事实表 actual_status="pending"，验证贪心结论是否正确。

增加 actual_status="pending" 和 assert greedy != actual_status，显示最高概率输出与真实状态可能不同。

面试时怎样表达边界

可以这样组织回答：“我先区分生成能力和事实来源。模型输出是条件生成，token 窗口是本次输入容量；采样参数调整候选输出的分布，不提供真实性保证。订单类任务要通过认证后的只读查询取得最新状态，记录证据时间，对缺失或冲突的信息表达不确定；上下文按预算装配，并用固定事实题与证据忠实性题分别评估。”这比只说“降低温度、加 RAG 就能消除幻觉”更完整，因为它说明每个措施解决了什么、还没有解决什么。

01 · 为什么低温度不能保证退款回答正确？

对应概念：采样为何让同一个问题出现不同回答

展开参考答案与评分要点

温度影响输出选择的随机性，不会建立支付系统连接，也不验证候选事实。若最高概率续写是“到账”，低温会更稳定地产生错误。应从受控查询取得状态、时间与证据，证据缺失时明确无法确认。

检查：说清采样作用；区分统计偏好与外部真值；给出证据方案。

02 · 窗口 1000，预留输出 200，规则 100，工具 150，历史 500，证据 150，能直接发送吗？

对应概念：上下文窗口是容量约束，不是可靠性承诺

展开参考答案与评分要点

输入为 900，连同预留输出共 1100，超过该教学假设的总预算。可用输入上限为 800，至少压缩 100；优先删重复历史、外置大结果，保留规则与关键证据。真实接口还应核验分别的输入和输出限制。

检查：算出 1100 与超出 100；说明不能简单截掉关键约束。

03 · 模型引用了一篇文档，为什么仍可能幻觉？

对应概念：把一个错误回复拆成可验证链路

展开参考答案与评分要点

引用标记可能是生成的，原文可能没被检索到、片段不支持结论、文档已经过期。需要验证引用存在且可访问、结论受该片段支持、时效满足问题，并对冲突证据进行处理。

检查：覆盖来源存在、支持关系、时效三个层次。

04 · 设计一个离线客服生成评测，怎样避免只测流畅度？

对应概念：把一个错误回复拆成可验证链路

展开参考答案与评分要点

建立订单事实表与固定查询结果，包含到账、处理中、拒绝访问和超时。评估答案与事实是否一致、是否编造证据、权限错误时是否泄露、缺结果时是否拒绝确认；另计语言清晰度。保留输入与工具观察便于归因。

检查：至少包含正确、缺证据、越权三个切片，并分开评估事实与表达。

容易踩的坑

  • 把字符数当精确 token 数
  • 把低温或结构化格式当真实性保证
  • 把数据库里的历史等同于模型本次已经看到的上下文

这一课的验收

能独立画出生成与查证的两条链，并用一个反例说明低温、长窗口和流畅语言各自不能保证什么。
