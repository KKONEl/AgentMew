场景：对话越来越长，助手却忘了“只生成草稿”

用户第一轮说：“帮我整理邮件，但只生成草稿，不要发送。”二十轮之后，工具返回了大量邮件正文，系统为了节省空间只保留最近十条消息。模型看到新的邮件内容，决定调用发送工具。这不是简单的“提示词不够强”，而是上下文构建删除了决定下一步行动的约束。上下文工程要解决的，是每次决策前到底给模型看什么、从哪里来、怎样组织，以及哪些边界由代码持续执行。

Prompt Engineering 关注指令、示例与输出格式等设计；Context Engineering 的范围还包括检索、工具 schema、对话历史、工作状态、长期记忆和工具结果处理。两者不是互斥路线，写好提示只是整个信息管道的一部分。即使上下文明确写着不要发送，运行时也应限制发送权限，避免把安全完全押在模型服从性上。本课教学例是教练补充，原文中的框架和面经主题不是无条件适用的生产定律。

先定义一次决策的最小充分材料

针对邮件任务，先列出目标、约束、当前进度、候选操作所需证据。目标是“生成回复草稿”，约束包括“不可发送”和“不得承诺未确认日期”，当前进度可能是“已读取邮件 E7，尚未核对库存”，证据是客户要求与库存查询。与此无关的旧寒暄、重复工具日志和整篇历史文章可以不进本次上下文。

材料要分层。受信规则与当前用户指令、结构化状态、必要历史、外部观察应有清楚来源和边界。检索文档、邮件正文、网页等都是数据，不应因为它们“看起来像命令”就获得系统级权威。角色分层和明确引用可以降低歧义，但不能单独消灭提示注入；涉及权限的字段必须由运行时绑定，外部文本不能改写授权。

一个可计算的预算例子

设教学预算为 200 个单位，预留输出 40，输入上限 160。固定规则与任务目标占 30，工具描述占 35，当前状态占 20，剩下 75 分配给近期对话和检索证据。若单个工具结果就有 300，不能先塞进模型再让模型摘要；应该在结果进入模型前截取必要字段、聚合、分页或存成可引用产物。原始数据需要有权限与生命周期，避免摘要引用了已经被删除或无权读取的内容。

生产系统的预算使用实际模型计量，考虑消息封装、工具 schema 和预计输出；本课实验用字符串长度作可观察代理，不声称一个字符就是一个 token。还应记录每类材料占用与被丢弃原因，这样发现某类任务经常因证据挤出而失败时，能调整分配而不是反复修改一句提示词。

压缩不是任意缩短

常见方法是保留近期原文，对较早历史生成摘要，将可检索原始材料外置。重要的是摘要必须保留决定行动的字段：资源 ID、用户否定约束、审批范围、已完成动作、待确认项和证据引用。把“没有授权发送”缩成“处理邮件”，文字更短，却改变了行为边界。把“订单状态未确认”缩成“订单正常”，则把未知改成了肯定。

可以为任务设计稳定的结构化摘要：goal、constraints、completed、pending、evidence_refs、version。每次压缩保存版本与原文范围，避免不断对旧摘要再摘要却失去恢复路径。遇到冲突时记录两个候选事实、各自来源与时间，不要让摘要模型为了流畅擅自选择一方。某些关键承诺或原始条款需要逐字保留，另一些背景可以概括，压缩策略应依任务损失函数决定。

已解例：压缩一段邮件工作记录

原记录包含：“目标是回复客户；只做草稿；客户问 E7；已经查库存但服务超时；上次活动文案用活泼语气；未确认库存前不能承诺明天发货。”一个可用摘要保留 goal=生成 E7 草稿，constraints=[不可发送，不承诺未确认发货日期]，pending=[重新核实库存]，evidence_refs=[E7, inventory-call-3]，status=库存未知。旧活动语气是否保留，要看它是否是本次任务仍然有效的偏好。

收到“继续”时，下一步是补查库存或生成含不确定说明的草稿，不能跳到发送或承诺日期。这说明压缩质量应与决策连续性相关，而非只评文字相似。两份摘要用词不同，只要保留必需字段、产生同样合规行动，可能同样好；一份摘要语言漂亮但改变授权范围，就不合格。

WORKED EXAMPLE / 从刚才的原理到这份代码

构造受保护字段的预算装配器

把正文的邮件 E7 案例与下方代码逐一对齐：state.goal 是 draft E7，constraints 只有 never send，pending 是 verify stock，refs 是 mail:E7。程序不会生成摘要，而是把已经整理好的这四项状态序列化成 protected；它长94个字符，budget 再加30得到124。

候选 evidence 的内容 stock=unknown 长13，recent 的 user:continue 长13，old_history 是100个 x；先放94字符的状态，再依次放两段13字符，used 最终为120，剩4，旧历史因此放不下。selected 的名称必须恰好是 state、evidence、recent。

接着恢复 JSON，分别检查 never send 和 verify stock，三行 stdout 就在报告选择结果、保留的约束与下一步。边界演示把原始 constraints 改成空列表，装配本身仍可能通过，但恢复后第19行会断言失败，说明不超预算与语义完整是两个独立验收条件；程序并不会自动找回漏掉的原文。

对应刚才的讲解：已解例：压缩一段邮件工作记录。本案例的运行范围：用字符数观察上下文预算和约束保留，不等同于真实token计量。

这份小实验能验证什么、还没实现什么

先把代码与概念对上

受保护状态先占预算，证据与近期消息再按顺序进入；100 字符旧历史没有空间，被跳过。恢复 JSON 后检查否定约束与待办，验证装配未丢行动必需信息。真实系统应替换长度函数并对带消息包装的完整输入计量。

完整参考实现 · 带行号供演示对照
import json

state = {"goal": "draft E7", "constraints": ["never send"],
         "pending": ["verify stock"], "refs": ["mail:E7"]}
protected = json.dumps(state, sort_keys=True, separators=(",", ":"))
candidates = [("evidence", "stock=unknown"),
              ("recent", "user:continue"), ("old_history", "x" * 100)]
budget = len(protected) + 30
selected = [("state", protected)]
used = len(protected)
for name, text in candidates:
    if used + len(text) <= budget:
        selected.append((name, text))
        used += len(text)
assert used <= budget
names = [name for name, _ in selected]
assert names == ["state", "evidence", "recent"]
restored = json.loads(selected[0][1])
assert "never send" in restored["constraints"]
assert restored["pending"] == ["verify stock"]
print("selected:", ",".join(names))
print("constraint:", restored["constraints"][0])
print("next step:", restored["pending"][0])

运行后应看到

selected: state,evidence,recent
constraint: never send
next step: verify stock
在同一案例上改一个条件 1：预算比 protected 长度更小应怎样处理？

先断言必需状态自身可容纳，否则明确返回 budget_insufficient，缩减工具定义、切换分阶段决策或调整产品策略；不能静默截断 JSON。

在同一案例上改一个条件 2：给 evidence 增加 refs，如何防止引用悬空？

维护引用到原始产物的映射，在装配前校验引用存在、当前身份有权限、未过期；失败就补读或把证据标记不可用。

怎样验证上下文工程

先做字段级检查，确认资源 ID、否定约束、待办与引用没有丢。再做任务级回放：用相同工具环境与验收标准，比较压缩前后的下一步动作、最终产物、费用与失败率。测试集要覆盖长对话、否定表达、用户纠正、工具结果超时和相互冲突资料。不能只请同一个摘要模型评价“摘要是否完整”，这容易重复它自身的盲点。

面试时可以这样表达：“我把上下文当受预算约束的工作集，先保护目标、授权和状态，再按任务相关性装配证据。长结果在工具边界处理，摘要保留可恢复引用和未知状态，压缩版本用字段检查加任务回放验收。提示词、检索与记忆都是管道组件，运行时权限仍独立执行。”这样的回答把提示词设计连接到了可测系统行为。

01 · 为什么按最近十条消息截断可能破坏任务？

对应概念：压缩不是任意缩短

展开参考答案与评分要点

消息长度差异很大，条数不是 token 预算；旧消息可能含目标、否定约束和授权。应将关键状态提取到受保护工作集，按真实计量选择近期原文并保留旧文引用。

检查：长度与语义两种风险都要说到。

02 · 把“状态未确认”压成“状态正常”错在哪里？

对应概念：压缩不是任意缩短

展开参考答案与评分要点

把认识上的未知变成业务上的肯定，改变下一步决策。摘要必须保留未知与待确认项，不能为了短或流畅补全事实。需要字段规则和回放验证发现这种错误。

检查：区分未知与正常，说明行动后果。

03 · 如何处理单次 20MB 的查询结果？

对应概念：一个可计算的预算例子

展开参考答案与评分要点

在工具或执行边界限体积，原始数据存为带权限与生命周期的产物，返回 schema、计数、摘要和引用；按需分页、过滤、聚合，再做 token 预算。不先把原始数据塞给模型。

检查：边界处理、原文引用、按需读取三个层次。

04 · 两份压缩摘要字面差异很大，怎样比较质量？

对应概念：怎样验证上下文工程

展开参考答案与评分要点

检查必需字段、来源和约束，再在同一环境回放任务，比较行动合规、验收成功率与资源成本。字面相似只是辅助，不能替代行为一致性和证据保真。

检查：字段检查加行为回放，不只文本相似。

容易踩的坑

  • 只按消息条数控预算
  • 摘要丢掉否定约束或把未知写成已确认
  • 用外部网页内容覆盖受信指令和运行时身份

这一课的验收

能给邮件任务写出受保护状态 schema，并证明压缩前后“继续”不会触发越权发送或编造库存。
