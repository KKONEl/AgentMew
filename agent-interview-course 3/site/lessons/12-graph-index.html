为什么需要把关系显式保存

三段文档分别写“张老师指导小李”“小李参与项目X”“项目X由研究所Y资助”。用户问张老师的学生里谁参加了Y资助的项目。单次向量检索可能只找到第一段；图表示把实体作为节点、关系作为边，允许围绕关联展开证据。向量RAG并非逻辑上不能多跳，而是单次相似检索容易漏链，图给了一种显式组织方式。

广义GraphRAG指利用图结构增强检索与生成的一类方法。微软GraphRAG是其中具体系统，强调从文本抽取知识、层级社区和社区报告，用于局部与全局查询。不能把一切知识图谱问答都说成2024年微软才发明，也不能假定所有GraphRAG必须采用完全相同的社区机制。官方概览

构图第一步仍是高质量文本

解析和切块需保留实体所在句子的条件、否定与时间。例如“计划加入项目X”不能抽成“已经参与X”；“不是导师”不能抽成导师关系。每条抽取结果关联text_unit_id、文档版本和原始位置。没有出处的边只是一个无法核验的断言，图画得再漂亮也不能证明真实。

抽取对象可包含实体名称、类型、描述，关系的起点、终点、描述与权重。描述保留解释信息，原文保留最终核验入口。多轮抽取可能提高覆盖，也增加成本与重复结果，需要看边/实体的精度、召回和下游任务收益，而不是追求图越大越好。

实体消歧：合并错误比漏合并更隐蔽

“微软”和“Microsoft”可能同一组织，但两个叫“王伟”的员工不能只靠名字合并。消歧要综合类型、组织、上下文和稳定标识。漏合并使一人被拆成两个节点导致关系断裂；误合并会把不同人的关系连通，制造不存在的多跳路径。实体合并需要保留别名与决策依据，对模糊情况可保持分离等待确认。

社区是什么，为什么要摘要

图中的社区是连接较密的一组节点，可以用层级聚类得到粗细不同的分组。社区不等于公司的部门，也不保证每组都有自然语言上明确主题。把实体、关系和相关文字汇总成社区报告，有助于后续全局综合，代价是索引时大量生成与摘要误差。官方索引流程

教材将Level0写为最细再逐层变粗，这个方向不应照背。社区level的意义取决于实现；微软层级中根/较粗层从0开始，后续层是更细划分，实际以固定版本数据和文档为准。面试更重要的是能说明粗层覆盖广但细节少，细层更细却消耗更多查询与上下文，而不是背层号。

已解例：三条关系如何变成可审计答案

建立T→指导→L、L→参与→X、X→资助方→Y，每条边带doc_id。查询时沿关系找出路径，再回原文确认时间、参与状态和人物身份。如果资助关系在2024年结束，而参与是2026年，忽略时态会给出看似连通但业务上不成立的答案。图路径是候选证据，不是自动完成因果证明。

图的方向也要明确：“A指导B”与“B指导A”含义不同；检索时可为邻域扩展建立无向索引，但推断关系时仍需保留语义方向。物理邻接和语义谓词不能混为一谈。

WORKED EXAMPLE / 从刚才的原理到这份代码

从三元组推演关系链

刚才的已解例给出张老师→小李→项目X→研究所Y这条关系链。下面三条edges对应这三份资料。每条记录是(起点,关系,终点,来源)：例如第二条把小李、参与、项目X和doc2放在一起。程序用集合与列表推导式把这些关系连接起来，让你手工核对“哪一步保留谁”。

第6行按指导关系取终点b，得到学生小李；第7行找到资助方为研究所Y的项目，得到项目X；第8行只保留同时满足“人属于学生集合、项目属于资助项目集合”的参与记录。因此hits只能是[(小李,项目X,doc2)]。最后的输出把路径和三个来源展示出来，和本段的图相互对应。

失败分支只把第6行的b错写成a。代码仍然能运行，但students会变成张老师，后面的参与连接得到空列表，原断言暴露错误。这让正文“保留关系方向”成为可观察的程序行为。这个小实验不是完整GraphRAG构建器：实体与关系已经人工标好，未调用LLM、Leiden或摘要。社区与离线索引在前面理论段解释；此处只拿其中的关系连接机制做实作。

对应刚才的讲解：已解例：三条关系如何变成可审计答案。本案例的运行范围：关系已人工标好，程序验证方向和集合连接，不负责自动抽取或社区检测。

完整参考实现 · 带行号供演示对照
edges = [
    ("张老师","指导","小李","doc1"),
    ("小李","参与","项目X","doc2"),
    ("项目X","资助方","研究所Y","doc3"),
]
students = {b for a,r,b,s in edges if a == "张老师" and r == "指导"}
funded = {a for a,r,b,s in edges if r == "资助方" and b == "研究所Y"}
hits = [(a,b,s) for a,r,b,s in edges if r == "参与" and a in students and b in funded]
assert hits == [("小李","项目X","doc2")]
print("小李 → 项目X → 研究所Y")
print("证据：doc1, doc2, doc3")

运行后应看到

证据：doc1, doc2, doc3
在同一案例上改一个条件 1：加入另一个同名小李后如何避免误连？

使用person_id而非display_name连接，保留别名和组织；没有足够证据时不合并。

在同一案例上改一个条件 2：给关系加valid_from/valid_to后如何处理历史问答？

按业务事件时间过滤所有边，确认各关系有效期交集符合问题；保留原文版本引用。

更新、成本与适用边界

新增文档可能改变实体描述、边权、社区和报告，需要考虑增量更新、版本一致性与失效范围；不意味着任何实现每次都必须全量重建。反过来，也不能只追加一条边就假定所有摘要已同步。先建立向量/关键词基线，再测图在多跳、关系查询或综述中的收益。精确查订单金额通常SQL更简单。小图实验只演示显式关系与来源，不执行LLM抽取或Leiden社区检测。

01 · 两个王伟为什么不能直接合并？

对应概念：实体消歧：合并错误比漏合并更隐蔽

展开参考答案与评分要点

同名不是同实体。需组织、身份标识、时间等上下文支持，模糊时保持独立。误合并会让不同人的边连通，创造虚假多跳答案。

检查：说明下游错误路径。

02 · 图路径存在就代表结论成立吗？

对应概念：已解例：三条关系如何变成可审计答案

展开参考答案与评分要点

不保证。抽取可能错误、边有方向与时间条件、节点可能误合并。需检查原文、版本、谓词与业务适用性；相关关系也不等于因果关系。

检查：至少覆盖两类约束。

03 · 所有GraphRAG都要有社区摘要吗？

对应概念：为什么需要把关系显式保存

展开参考答案与评分要点

不。广义图增强检索可用已有图和固定图查询；微软GraphRAG使用层级社区和报告支持特定检索方式。应说明讨论的是哪类方法或具体实现。

检查：分清方法家族与具体系统。

04 · 图新增一条边，为什么摘要也可能要变？

对应概念：更新、成本与适用边界

展开参考答案与评分要点

边可能改变实体描述、社区归属或主题关系，派生报告依赖这些内容。应追踪依赖与失效范围，选择增量/局部重算或版本构建，不能只更新图忽略派生层。

检查：解释派生数据一致性。

容易踩的坑

  • 同名实体直接合并
  • 把图邻接当因果证明
  • 背错社区层号且不看实现
